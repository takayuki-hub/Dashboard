## 背景・目的

### 解決すべき課題
現在、アプリライフサイクルイベント（起動、終了）の記録は実装されていますが、ユーザーがどの画面を訪問したかを追跡する画面遷移イベントが未実装です。画面遷移イベントは、ユーザー行動分析の中核となり、どの機能が最も利用されているかを把握するために必須です。

🔵 **信頼性レベル**: 青信号（要件定義書 REQ-201、ユーザヒアリング2026-09-12 Q4より確実）

### 達成目標
1. AnalyticsRepositoryに`logScreenView`メソッドを追加
2. 各featureモジュールのViewModelで画面表示時にscreen_viewイベントを記録
3. 画面名定数の管理（AnalyticsEventsまたは新規ScreenNamesオブジェクト）
4. イベントパラメータの正確性を保証するテストの作成

### 非目標
- ユーザー操作イベントの実装（TASK-0006で実装）
- エラートラッキングの実装（TASK-0007で実装）
- カスタム画面遷移アニメーションのトラッキング

```kotlin
override suspend fun logScreenView(screenName: String, screenClass: String) {
    withContext(Dispatchers.IO) {
        val bundle = Bundle().apply {
            putString(FirebaseAnalytics.Param.SCREEN_NAME, screenName)
            putString(FirebaseAnalytics.Param.SCREEN_CLASS, screenClass)
        }
        firebaseAnalytics.logEvent(FirebaseAnalytics.Event.SCREEN_VIEW, bundle)
    }
}
```

## エッジケース・考慮事項

### エラーハンドリング

#### ViewModel初期化中の例外
- **シナリオ**: logScreenView実行中に例外が発生
- **対応**: viewModelScopeによる例外ハンドリング、アプリクラッシュを防止
- **影響度**: 中
- **信頼性**: 🔵 Kotlin Coroutines仕様より

#### AnalyticsRepository未注入
- **シナリオ**: ViewModel初期化時にAnalyticsRepositoryがnull
- **対応**: Hiltによる自動注入、nullableにしない
- **影響度**: 高
- **信頼性**: 🔵 Hilt仕様より

### パフォーマンス考慮事項

#### ViewModel初期化遅延
- **課題**: logScreenView呼び出しがViewModel初期化を遅延させる可能性
- **対応**: viewModelScope.launch（非同期）で実行、UIスレッドをブロックしない 🟡 *NFR-0005-001より*
- **影響度**: 低

#### 画面遷移頻度
- **課題**: ユーザーが画面を頻繁に遷移した場合のイベント送信負荷
- **対応**: Firebase Analytics SDKが自動的にバッチング処理
- **影響度**: 低
- **信頼性**: 🔵 Firebase Analytics SDK仕様より

### セキュリティ考慮事項

#### PII除外確認
- **課題**: 画面名、画面クラス名にPIIが含まれないことを確認
- **対応**: 両方とも技術的な識別子のみ、ユーザーデータなし 🔵 *NFR-0005-003より*
- **影響度**: 高

#### 画面クラス名の露出
- **課題**: 画面クラス名が難読化後も意味を持つか
- **対応**: ProGuardルールで保持、またはハードコード文字列に変更検討
- **影響度**: 低
- **信頼性**: 🟡 ProGuard設定から妥当な推測
